An SBOM generator is easy to test badly. Point it at a handful of tidy repositories, check the output parses, and everything looks fine. The failures that matter are not crashes. They are documents that validate cleanly, exit zero, and describe the wrong software.

So we ran [sbomify-action](https://github.com/sbomify/sbomify-action) against 500 popular open source projects and looked at every SBOM it produced.

## How the test was set up

Three decisions did most of the work, and we got two of them wrong the first time.

**Every project is scanned at a release, not at `master`.** Nobody generates an SBOM for a branch. An SBOM describes something you ship, and what you ship is a release. Of the 500 projects, 401 resolve to a GitHub release, 60 to a version-sorted tag, and 39 have never tagged anything and are marked as such in the results rather than quietly mixed in.

**One pinned image for the whole run.** The action is pinned by digest, not by tag, so a run that takes most of a day cannot have its subject change underneath it. Every number below comes from one build.

**The harness asks the tool what it would do.** It does not reimplement the selection logic. This sounds obvious. It is the thing we got wrong twice, and we will come back to it.

## What it found

### PHP projects produced empty SBOMs, silently

A PHP library typically gitignores `composer.lock`, because the consuming application resolves it. That means most PHP on GitHub arrives as a manifest and nothing else.

Without Composer available, cdxgen cannot read a `composer.json` at all. It stops with "No composer version found", the generator chain falls through to syft, and syft writes a document with **no components and exit code zero**. No warning, no failure, just an SBOM that says the project has no dependencies.

The toolchain existed. Our bundle repository had been building and publishing a PHP bundle for some time. Nothing in the action declared it, so the lookup returned nothing and the whole ecosystem quietly degraded. Wiring it up took three lines of manifest.

Measured on real libraries with the lock file removed:

| Project       | Before       | After |
| ------------- | ------------ | ----- |
| guzzle/guzzle | 0 components | 7     |
| slimphp/Slim  | 0 components | 7     |

### Two concurrent runs corrupted each other

The bundle cache was guarded by a `threading.Lock`, which coordinates threads inside one interpreter and nothing else. Two _processes_ sharing a cache, which is two jobs on one CI runner, both found the cache empty and both unpacked into it. The loser hit `ENOTEMPTY` and failed with an error naming neither cause nor remedy.

Separately, the JVM bundle pointed `GRADLE_USER_HOME` at a shared path and assigned it _after_ reading the caller's environment, so exporting it to separate two builds did nothing. The only fix available from outside was to stop running two builds at once.

Neither is visible in a single CI job. We only saw them because the harness runs several copies of the action at the same time.

### A broken build wrapper cost the project its SBOM

Projects pin their build tool with a wrapper, and the action prefers it, because RxJava pins Gradle 7.6.4 and that is a deliberate choice. But apache/kafka gitignores `gradle-wrapper.jar`, so `gradlew` downloads it on first run using curl, which our image does not carry:

```
/workspace/gradlew: 207: curl: not found
Error: Unable to access jarfile /workspace/gradle/wrapper/gradle-wrapper.jar
```

The native generator failed and the chain fell through to a weaker one. For okhttp, that difference is 288 components against 34. apache/flink hit the same wall differently: its `mvnw` validates its own jar against a checksum and refuses.

Now, when a project's wrapper cannot run, the action falls back to the build tool it ships rather than to a worse generator.

### The SBOM that described curl's test suite

curl is a C project. It has no lockfile the action recognises, so discovery finds only this:

```
.github/scripts/requirements.txt
projects/Windows/tmpl/curl.sln
tests/requirements.txt
tests/http/requirements.txt
```

The rule was "pick the shallowest", which chose `tests/requirements.txt`. The result was a one-component SBOM named "curl" describing curl's Python test harness. It validates. It has the right project name on it. Nothing about it looks wrong.

Across the corpus, 60 projects have no lockfile at their root, and 29 of those would build their SBOM from a tooling directory:

| Project       | Would build its SBOM from                              |
| ------------- | ------------------------------------------------------ |
| Homebrew/brew | `docs/Gemfile.lock`                                    |
| NixOS/nixpkgs | `ci/github-script/package-lock.json`                   |
| ocaml/dune    | `doc/requirements.txt`                                 |
| dotnet/efcore | `benchmark/EFCore.Benchmarks/EFCore.Benchmarks.csproj` |
| emqx/emqx     | `scripts/sbom/requirements.txt`                        |

That last one is an SBOM tool whose SBOM would have described the dependencies of its own SBOM script.

Lockfiles under `tests/`, `docs/`, `examples/` and similar are now listed but not selected by default, with a note explaining why. When a project has _nothing else_, it still gets selected, and the wizard says plainly that the resulting SBOM describes how the project is built rather than what it ships.

## The part worth reading: three of the bugs were ours

We set out to find defects in the action. The first three we found were in the thing measuring it, and every one made the tool look worse than it is.

**The harness cloned the default branch.** We were measuring a case that does not occur. That produced a finding about placeholder version numbers, and a pull request to fix it, before anyone asked whether the problem existed at a release checkout. Both were withdrawn.

**The harness reimplemented the tool's file-ranking logic**, and the copy had been truncated. For any ecosystem outside that subset, every candidate scored the same and ties broke alphabetically. Alamofire, a Swift package, was scanned as `Gemfile.lock` and produced an SBOM claiming it was a Ruby gem with 55 fastlane dependencies. Once the harness called the tool's own ranking instead of restating it, the same project returned an honest refusal explaining that `Package.swift` needs a `Package.resolved` beside it.

**The harness ignored a guard the tool already had.** It reached past the tool's exclusion of vendored repositories, so flutter/flutter appeared to resolve as Rust via a vendored crate the tool would never have selected.

Every one of these has the same shape. A copy of a fact is a second thing to drift, and when it drifts, the harness reports the drift as the product's behaviour. It is the same rule we already apply to our toolchain bundles, where each bundle states its own facts for consumers to read rather than having consumers keep their own copy. We just had not applied it one layer out.

There is a more uncomfortable version of this. A test harness that is wrong in the _flattering_ direction produces a green wall and nobody investigates. We found ours because they were wrong in the other direction, which is luck rather than method. The method we settled on is duller: for every finding, write down which harness assumption it depends on, and check that assumption before believing the finding.

## What we would tell you to check in your own SBOMs

Most of what we found shares one property: the failure is quiet. The document validates, the job goes green, and the content is wrong. Three checks catch most of it.

**Does the component count look plausible?** An empty SBOM and a 400-component SBOM are both obvious. A 1-component SBOM for a large C project is the one that slips through.

**Is the root component your project?** If the purl says `pkg:gem/...` and you do not ship a gem, something upstream chose the wrong input file.

**Did anything get chosen from `tests/` or `docs/`?** Those describe how your project is built. They are not what you ship, and an SBOM that lists them is answering a question nobody asked.

If you want the action to check the first of these for you, it does now.
